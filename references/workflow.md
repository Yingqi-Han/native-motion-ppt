# 工作流程

## 一个入口完成制作与验收

依赖就绪后优先 accept_project.py，规则见 [一键验收](acceptance.md)。它将下述设计步骤的执行结果放在独立目录，保留源文件与各类证据，不取代前期内容和审美判断。生成后查看实际关键帧，记录审阅结论并重新核对交付包。

## 内容到镜头

写明受众、场合、需要观众记住或理解的结论。每页只安排一个主要理解任务；确需多个层次时，用语义分组展开。

先画静态主体和结束状态，再设计如何到达这个状态。用“入场 → 理解 → 变化 → 停留 → 下一页”检验节奏。内容页可以长时间停留，宣传式短片可以更紧凑；不要把15秒示例的时长套给学术报告。

页面不必处处同构。统一来自字体层级、色彩、边缘、视觉主角与运动规律；版式要服从不同页面的作用。

## 新建或重做

1. 读取原稿；保存原始内容和关键数据。
2. 设计2–3页代表性页面，先检查真实排版、字体和运动。
3. 将被认可的视觉语言用于其余页面，变化构图与镜头尺度。
4. 编写源 JSON；preview 提供可定位的时间线。需要双输出时，先渲染设计视频，检查动作、节奏与转场。
5. 由同一份已检查的数据 build 手动与自动 PPT；check 渲染全部实际页面并检查动画导入。对播放器难以稳定实现的动作作原生替代，同步修改设计视频。
6. 在目标 WPS / PowerPoint 桌面版本放映并录屏，对照设计视频修正。没有目标环境时标明待复测，再交付可检查的文件及已有证据。

美化可能需要重建几何和层次，enhance 命令主要负责加动画，不会自动重新设计所有页面。Agent 应承担内容、视觉叙事与版式判断。

## 现有 PPT

inspect 提取顶层对象的 id、名称、文本和位置。先查看实际页面，再按逻辑单位写 plan：论点及证据可以一起出现，结论单独成为一次点击。

plan 只针对列出的页面；其余页保留。已有动画默认跳过。替换动画必须在新输出文件进行。复杂组可作为一个整体目标；需要组内分步时先重建或拆分组合。

## 从视频发展为 PPT

优先读取 Remotion 源码中的对象、字体、几何与时间。抽关键帧用于判断镜头和版式。将可映射的效果写入共用 JSON；不可映射的效果另做视觉替代。

没有源对象的 MP4 只能提供参考帧。重新建模、排版和编排，交付说明保留了哪些运动，而不是声称恢复视频内部对象。

## 双输出

共用 JSON 是编辑源。PPT 后端生成几何和原生时序；浏览器/Remotion 后端逐帧求值。两端共享对象身份、文字、颜色、几何、路径、时长和触发约定。

浏览器会按 clicks 约定模拟演讲者点击；手动 PPT 等实际点击。两端不是同一个渲染器，最终质量分别检查。

顺序是：**设计视频 → 对应原生 PPT → 目标桌面放映核对**。先做视频是为了确定设计，不是用视频证明 PPT 的播放效果。目标放映中发现问题，需要同时更新共用数据和两个输出。

保留三种独立产物：design-preview.mp4 是代码设计预演；deck.pptx 是原生演示文件；player-recording.mp4 是桌面放映录屏，只有实际录制后才存在。delivery-provenance.json 记录来源与验证状态。录屏步骤见 [实机放映核对](desktop-playback.md)。

## 文件交付

至少有 deck.pptx、project.json、README、QA 结果和页面预览。较完整交付包含脚本、依赖、字体许可、PDF、关键帧和自动版；用户需要视频时另附 MP4。

## 连续运动复查

```bash
python scripts/build_demo.py --video
python scripts/check_motion.py --url http://localhost:3020/preview.html --object sculpture --out output/qa/motion
```

build_demo.py 自动启动并关闭检查用服务器；第二条命令用于已在运行的项目预览。check_motion.py 在每一个计划帧读取主体的实际 SVG 位置与尺寸，另检查跨场边界两侧的精确位置；--max-step 可调整每帧最大中心位移阈值。报告与拼图放在指定目录。

数值检查用于查跳动，不代表运动一定美观。仍需观看视频，检查速度、停顿、光照是否与动作一致。示例原生 PPT 的大球在翻页前回到静态姿态，因此不依赖预览器修正来隐藏原生路径问题。

源码、输入与生成文件分开。npm 依赖在生成项目中用锁文件安装，避免软链接到其他视频项目。历史项目可归档，但保留原始交付、编辑源与移动记录；只清理可以明确重建的缓存。
